# ArenaHub security review and implementation record

17 November 2026. Scope: the current working tree, including prior module work, for the user's confirmed **publicly hosted website and API**. Available devices: Windows PC and iPhone; Android implementation is required now, physical testing later.

## Result

Several concrete weaknesses and integration gaps were fixed. There is no basis to certify the entire system as secure or to promise that every installed cheat will be detected. The monitor is now a working, consent-based known-indicator collector with explicit coverage limits. Public production settings, signed native releases and real-game/device validation remain required.

The review used the official OpenAI GitHub [security-best-practices skill](https://github.com/openai/skills/tree/main/skills/.curated/security-best-practices) and [security-threat-model skill](https://github.com/openai/skills/tree/main/skills/.curated/security-threat-model), retrieved into a workspace-local tools folder. React, general frontend and Express guidance was applied. They are review instructions, not an independent penetration-test certification. User authorization already covered fixing issues; no production deploy or real-account mutation was performed.

## Corrected findings

**SEC-001 - High: GSI credential scope and misleading scanner freshness.** A credential written into Dota's game configuration previously shared device-control privileges. Game telemetry and media could also refresh the scanner timestamp. A holder could therefore submit device facts or keep a stopped scanner looking online. New Dota sessions receive a distinct hashed telemetry-only token; device/GSI capabilities are mutually rejected, and only device heartbeats update scanner freshness. Session end/expiry revokes both. Evidence: `server/integrityStore.ts:101` (`claim`, `byGsiToken`, `saveGsi`, media writers), `server/integrity.ts:189`. Regression tests exercise both token directions, liveness and revocation. Re-pair old Dota sessions after upgrading.

**SEC-002 - Medium: recording-off policy was enforced only by cooperative clients.** A paired client could upload media despite the staff recording setting. The API now rejects both media and chunked-upload routes before body parsing when recording is disabled. Evidence: `server/integrity.ts:145` (`recordingAllowed`); the per-match recording API test verifies 403 and no stored files.

**SEC-003 - Medium hardening: browser protections and generic errors.** Production Express responses and generated Firebase Hosting configuration now include MIME/frame/referrer/permissions protections and CSP. The standalone join-page bootstrap is permitted by an exact SHA-256 digest; arbitrary inline JavaScript and eval are not enabled. CSP is deliberately omitted only for Vite development bootstrap. The policy is a script/embedding defense, not a complete resource allowlist. Generic body/500 errors avoid exposing internal paths/stacks. Evidence: `server/securityPolicy.mjs:5`, `server/securityHeaders.ts:5`, `server/app.ts:21`, `scripts/sync-security.mjs`. A real browser test verifies approved inline code executes and injected inline code does not. No exploitable stored-XSS sink was demonstrated by this review.

**SEC-004 - Medium hardening: unsafe pairing destinations and redirects.** Origin parsing bounds length and constrains normalized DNS/IP hosts, rejecting shell metacharacters, credentials, paths, fragments, whitespace, backslashes and quote/config injection characters before creating player commands or GSI files. The Windows/Android HTTP clients reject redirects. The agent asks the player to verify its destination before consent. Evidence: `src/lib/monitorAddress.ts:2`, `tools/integrity-agent/agentCore.ts` (`gsiConfig`), `server/integrity.ts:234`, Android `Api.kt`. This reduces injection/credential-forwarding risk; a malicious trusted organizer or compromised server is still outside this protection.

**SEC-005 - Medium: incomplete checks and overconfident labels.** Android package/overlay failures and Windows inspection failures are now reported, shown as limited coverage and scored for human review. Windows differentiates installed entries, running names and configured file fingerprints. Android compares configured signer hashes. A missing signer is not called an unsigned executable, a missing game certificate is incomplete inspection, and game key differences require publisher/region/key-rotation review. Empty findings do not assert clean play. Evidence: `src/lib/integrityRisk.ts:19`, `src/lib/integrityRisk.ts:184`, `tools/integrity-agent/windowsScan.ts:80`, Android `DeviceChecks.kt:37`, monitor session dialog. Self-reported data is still forgeable.

**SEC-006 - Medium: default Android cleartext traffic.** The prior APK allowed general HTTP transport, exposing credentials/recordings on untrusted networks. Standard builds now require HTTPS. An explicit build flag permits HTTP only to loopback/private IPv4 for isolated LAN tests. Both native clients refuse redirects. Debugging is disabled, and backup/device-transfer exclusions are explicit. Evidence: Android `app/build.gradle.kts:10`, `AndroidManifest.xml:23`, `Api.kt:10`, `res/xml/data_extraction_rules.xml`, `scripts/build-companion.mjs`. Final Android lint has no security-category findings; unrelated localization/resource warnings remain.

**SEC-007 - Functional/security integration: public monitor hosting.** The monitor UI previously hardcoded a same-origin event-laptop API; staff origin checks and the tunnel guard prevented a separate hosted API. It now uses the configured API base for sessions/settings/media and the explicit CORS allowlist. `INTEGRITY_HOSTED_URL` distinguishes full public hosting from the player-only laptop tunnel and requires HTTPS; conflicting modes fail at startup. Hosted staff routes remain available behind Cloudflare and still require active staff authentication. Lookup/throttle maps are bounded without clearing all active limits; GSI writes are throttled. Evidence: `server/publicAccess.ts:25`, `server/integrity.ts:53`, `server/cors.ts:36`, `src/components/admin/MatchMonitorView.tsx:29`. This does not make SQLite/ticket state safe for ephemeral or replicated hosting.

**SEC-008 - Medium privacy hardening: collection past an unreachable match deadline.** Native clients previously relied on a server expiry response to stop, so a disconnected client could keep collecting after its agreed match window. Both now schedule local expiry from the claimed deadline; Android discards late recording segments and cancels collection during service teardown. The Windows integration test simulates an unresponsive API and verifies timely local exit. Android static/build verification passed; physical-device confirmation remains required. Evidence: `tools/integrity-agent/agent.ts` (`main`), Android `MainActivity.kt`/`MonitorService.kt`.

## Existing controls checked

- Firebase ID-token verification, active profile checks, verified campus staff claims and student admission are shared by API authorization (`server/auth.ts:49`, `server/staffAuth.ts:6`). The preferred Admin SDK path verifies revocation; fallback behavior is documented.
- Firestore/Storage rules protect unpublished/private records, roles, evidence and account state. Emulator suites include negative access tests, not only successful operations (`firestore.rules`, `storage.rules`, `tests/*rules*`, `tests/server-auth.integration.test.ts`).
- Pairing is short-lived/single-use; tokens are high-entropy and stored hashed. Recording access requires staff or a short-lived single-file playback capability. SQL values use prepared statements. Download names are allowlisted, not arbitrary request paths (`server/integrityStore.ts`, `server/integrity.ts`).
- React renders untrusted text through JSX; the join page uses textContent. This pass found no runtime eval/Function or raw user-HTML rendering sink in `src/`/`server/`. URL/evidence validation and secret-free build checks already have regressions.
- Production dependency audit reported zero known vulnerabilities. This is a package-advisory result, not evidence against unknown or application-specific flaws.

## Remaining risks and release conditions

**R-001 - High integrity risk on an attacker-controlled device.** Players can modify user-mode software or forge reports. No kernel agent, hardware-backed reporting trust or publisher integration is implemented. Signed binaries improve distribution trust, not the truth of reports from a compromised OS. Unknown/hidden cheats, injected DLLs, inactive portable files and external hardware are outside current coverage. Use staff-controlled devices/observers for high-stakes matches. See ANTI_CHEAT_COVERAGE.md.

**R-002 - High release risk: unsigned/development-signed native artifacts.** The built Windows SEA executable does not have a valid release Authenticode signature; the APK uses a development signing key even though debugging is off. Do not broadly distribute these as trusted public releases. Organization-owned signing keys, trusted-channel fingerprints and real-device/game compatibility validation are not available in this workspace.

**R-003 - Medium availability/privacy risk: host configuration and capacity unverified.** TLS ingress, forwarded-client normalization, public Firebase rules, service-account IAM, storage permissions/encryption/backups, quotas and edge connection limits have not been inspected on a real deployment. The monitor uses one persistent Node process/private volume. In-memory limits and playback/upload state do not coordinate replicas; per-session limits are not a global storage quota. Require host-level capacity/backup/ingress verification before launch.

**R-004 - Medium operational risk: indicator and human-review quality.** Starter lists include legitimate software. No production cheat hashes were supplied or invented. Validate indicator provenance and false positives, separately record installation/running/fingerprint evidence, and use human case review. A referee observation or AI visual summary cannot prove installed cheating software.

**R-005 - Device validation pending.** Android build/lint and simulated report validation do not establish actual OEM visibility/capture behavior. iPhone browser simulation is not real Safari verification. Windows collector mechanisms were tested locally with harmless indicators; no live game/cheat compatibility claim is made.
